## Navigation architecture

- Use LaunchNav bottom tabs (Home, Record, Diary, Circle, Vision: the everyday journey) plus one safe-area-aware circular You-Are-Here dial from LaunchLayout as the only app navigation system; keep first-time onboarding linear; why: the core journey is always one tap away, everything else is one dial away.
- Account creation offers one start choice from `src/launch/onboarding/startPlan.ts` (tested): free 7 days (card at the start, first charge after the trial) or register fully (membership starts today) → card step → Who it's for (all audiences visible) → welcome → Questions → My snapshot; checkout honours the choice via `startTrial`; why: people choose when the first charge happens, and both paths share one set-up.
- Keep an unselected starting point distinct from a recovery identity using the shared neutral assessment bank; why: skipping a choice must never imply brain injury.
- `/launch/landingpage` is the single front door; `/`, `/start`, `/launch`, `/landing`, `/mvp` redirect there via `ToLanding` keeping query strings. Its banner offers only Log In (registered: trial or member) and Get Started (full registration); why: one obvious start, never lost.
- Get Started screens show `JourneySteps` (Create account → About me → Questions → My snapshot) with Save and finish later; why: people always know where they are and what is next.
- Landing buttons derive from `getEntryState` (new / returning / needsQuestions / hasSnapshot / member) in `entryRoute.ts`; why: labels must promise exactly where they lead, and returning visitors see Sign in, not sign-up.
- Home presents one current priority plus Record and See my day; secondary destinations belong in the You-Are-Here dial.
- Gentler Home and optional ongoing reflections use one user-scoped device-local daily-support store; gentler days expire by local calendar date and never mutate appointments or reminders, while reflection dates start only on explicit opt-in — why: reduce daily load without inferring discharge dates or clinical recovery.
- Calendar vision-focus disclosure, confirmed vision relationships and event priority highlights are user-scoped device-local presentation state; why: keep vision direction distinct from everyday priorities without changing schedules or promising cloud sync.
- Memory Bridge output choice (output_mode on meeting_recordings) is decided per recording and enforced in process-meeting-audio; why: one server path keeps transcript-only / actions-only / save-only consistent everywhere.
- Memory Bridge uses a recording-first open workspace and one saved-record list with the latest conversation first; uploads and quick notes use entry disclosures, while recorder and processing handlers remain in the Launch page — why: keep presentation coherent without duplicating records or changing capture contracts.
- Saved conversation details default closed and remember per-user device-local choices; explicit opens may expand only the requested record — why: prevent visual overload without hiding access.
- Memory Bridge's shared compact library filters title/reference metadata and date, groups by month, and pages loaded records in tens; capture handlers stay in LaunchMemoryBridge — why: keep growing histories browsable without changing capture or implying complete server-side search.
- Action origins share one disclosure that verifies the action-to-meeting relationship and uniquely matches quotes against available transcripts; never infer exact provenance from estimated timestamps or expose removed transcript excerpts — why: traceability must be accurate and retention-aware.
- Superseded page versions live in `src/pages/_archive/` (unrouted); old URLs redirect to current /launch pages — why: keep one live flow without losing earlier work.
- The launch assessment uses one versioned shared bank with every question tagged `tier` (quick = YES parts, full = MYRHYTHM letters); `?mode=full` runs the Full Picture on top of saved Quick answers and scores count answered items only; why: one bank keeps the free snapshot, history and calendar inputs consistent across both depths.
- Welcome starting style and explicit walkthrough progress use one user-scoped device-local store, shared by welcome, the existing map and LaunchLayout; why: support can be switched without changing assessment depth, membership or inferring completion from saved rows.
- Snapshot report priority areas are derived only from saved answers in `src/launch/compass/priorityAreas.ts` (tested); why: one ranking source keeps report, offer line and future Home focus consistent.
- Support Circle diary sharing goes only through security-definer RPCs (my_shared_diaries, circle_diary, circle_add_diary_item) gated by the per-member permissions.diary level, with private items masked as Busy; why: members never get direct row access to someone else's calendar_events.
- Signed-out access is decided app-wide by `SignedInOnly` around the router, using the allowlist in `src/launch/access/publicPaths.ts` (tested); why: one gate guarantees nobody sees past the landing page without signing in, including older unrouted-looking pages.
- Suggested diary times come only from `src/launch/scheduling/suggestSlots.ts` (tested), fed by saved assessment peak hours and existing events; why: one rule set for Home and conversation steps, never double-booking.
- Home shows at most 3 priorities plus one Next line (Dashboard or List view, remembered per user on device), with yesterday/tomorrow and extras folded; every item is edited in the shared `PriorityDetailSheet` against its original record; why: calm surface, detail on demand, one source of truth.
- Reminder timing and saved answers come only from `src/launch/reminders/reminderStages.ts` (tested); diary views announce changes through `diarySync.ts` so Home, calendar and the reminder card stay in step — why: one rule set, and an item answered in one place never keeps nagging in another.
